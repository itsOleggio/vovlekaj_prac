# Обработка лога работы веб-сервиса 

## Описание проекта 

Приложение для анализа логов сервиса и выявления аномалий в его работе.

Программа загружает лог-файл __(service_log.txt)__, парсит его и преобразует в структурированные данные. На основе этих данных выполняется:
- расчет ключевых метрик сервиса
- анализ распределения ошибок и статусов
- выявление аномалий latency (z-score)
- группировка аномалий в инциденты
- визуализация поведения системы во времени

Проект разделён на логические слои:
- `helpers/` — парсинг, статистика, детекция аномалий
- `components/` — UI (карточки, таблицы, графики)
- `App.tsx` — композиция и оркестрация данных 

### Функциональность

- __Обработка логов__
  - Парсинг строк логов в структурированный формат
  - Фильтрация битых и некорректных записей
  - Поддержка сервисов: auth, payments, notifications
- __Метрики__
  - Общее количество запросов
  - Распределение по сервисам
  - Распределение статусов (ok, error, retry, timeout)
  - Процент ошибок
- __Аномалии__
  - Детектирование отклонений latency с использованием z-score
  - Выделение аномальных запросов
  - Группировка аномалий в инциденты по времени
- __Визуализация__
  - График latency во времени
  - Отображение аномалий поверх временного ряда
  - Таблицы аномалий и инцидентов

### Технологии

- Vite

- Lodash


## Текстовый вопрос 

Да, в целом такие сбои можно пытаться предсказывать заранее, если в логах действительно присутствуют повторяющиеся паттерны деградации перед инцидентами. В обработанных данных видно, что инциденты не случайны: при общем `error rate` около __5.39%__ и __138__ зафиксированных инцидентах можно предположить наличие систематических ухудшений, особенно в сервисах с сопоставимой нагрузкой (`auth`, `payments`, `notifications`). 

Для построения предиктивной модели я бы использовал временные ряды метрик: `latency`, частоту ошибок, долю `timeout`/`retry`, а также интенсивность запросов по сервисам. Дополнительно полезно строить производные признаки — скользящие средние, экспоненциальное сглаживание, скорость роста latency и всплески дисперсии перед инцидентами. 

Задачу можно формализовать как бинарную классификацию: наступит ли инцидент в ближайшие N минут. В качестве базовых моделей подойдут градиентный бустинг __(например, CatBoost/LightGBM)__ или модели для обнаружения аномалий во временных рядах, а при наличии большого объёма исторических данных — LSTM или Transformer-подходы. 

Основное ограничение в таких данных — дисбаланс классов и слабая повторяемость инцидентов, из-за чего модель может переобучаться и давать ложные срабатывания. Также важным фактором является качество телеметрии: без стабильного сбора метрик и контекста нагрузки точность предсказаний будет ограничена.
